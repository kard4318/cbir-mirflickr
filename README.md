# CBIR: textual and visual image search over MIRFLICKR-25k

A content-based image retrieval engine built without Elasticsearch: a custom
**VP-Tree** index (plus brute force for comparison), a **FastAPI** JSON backend, a
plain **HTML/CSS/JS** client, and **SQLite** for paths, tags and metadata.

## Architecture

```
OFFLINE  scripts/build_index.py
  images ──► color / LBP / HOG (multiprocessing) ─┐
  MPEG-7 txt files ──► EHD / HTD parsing ─────────┼─► artifacts/features_<d>.npy
  tags, EXIF, license, annotations ──► SQLite ────┤   artifacts/cbir.sqlite
                                                  └─► artifacts/vptree_<d>_<metric>.joblib
ONLINE   backend/main.py (FastAPI)
  loads the artifacts once ─► /api/search (JSON) ─► frontend/ (served at /)
  images are served from their folder on disk under /images/...
```

| Folder | Content |
|---|---|
| `backend/descriptors/` | `color.py`, `lbp.py`, `hog.py` (computed), `mpeg7.py` (provided EHD/HTD parsers), shared `preprocess.py` |
| `backend/index/` | `vptree.py`, `bruteforce.py`, `distances.py` (L1, L2, histogram intersection) |
| `backend/db/` | SQLite schema and queries, metadata parsers |
| `backend/engine.py` | online search engine (loading, distance combination, keyword filter) |
| `backend/main.py`, `schemas.py` | FastAPI app and JSON models |
| `frontend/` | `index.html`, `app.js`, `style.css` |
| `scripts/` | `build_index.py` (offline phase), `run_evaluation.py` (metrics + benchmark) |
| `tests/test_vptree.py` | checks that the VP-Tree returns exactly the brute-force neighbours |
| `report_assets/` | generated CSV files, figures and `evaluation_summary.md` |

  mpeg7/homogeneoustexture/   1.txt ... 25000.txt (43 values each)                   - MPEG-7 HTD

## Run

```powershell
# 0. (optional) VP-Tree correctness test
python -m tests.test_vptree

# 1. OFFLINE: quick test on 1000 images, then the full base (~8 min: 4 min extraction, 4 min metadata)
python -m scripts.build_index --limit 1000 --out artifacts_test
python -m scripts.build_index

# 1b. OFFLINE: VGG16 deep features (CPU, 40-70 min, resumable: re-run the same command after Ctrl+C)
python -m scripts.extract_vgg16 --limit 200     # speed test only
python -m scripts.extract_vgg16                 # all images, then registers the descriptor
#    (re-run it after any full build_index: it only re-registers if the images did not change)

# 2. ONLINE: start the server, then open http://127.0.0.1:8000
uvicorn backend.main:app --port 8000
#    (serve the test index instead:  $env:CBIR_ARTIFACTS_DIR = "artifacts_test")

# 3. Evaluation (CSV + figures + summary in report_assets/)
python -m scripts.run_evaluation
```

### Using another image base (e.g. the "Objects" base)

All paths are configurable (`backend/config.py` or environment variables
`CBIR_IMAGES_DIR`, `CBIR_META_DIR`, `CBIR_ANNOTATIONS_DIR`, `CBIR_MPEG7_DIR`,
`CBIR_ARTIFACTS_DIR`), or on the command line:

```powershell
python -m scripts.build_index --images-dir D:\objects --no-mpeg7 --out artifacts_objects
$env:CBIR_ARTIFACTS_DIR = "artifacts_objects"; uvicorn backend.main:app --port 8000
```
Files named like `imN.jpg` / `N.png` keep the number N as their id. Otherwise ids
are assigned in alphabetical order. Without MPEG-7 files only color, LBP and HOG
are indexed.

## Descriptors

| Name | Source | Dim | Default metric | Details |
|---|---|---|---|---|
| Color | computed | 128 | histogram intersection | HSV joint histogram 8 (H) x 4 (S) x 4 (V), L1-normalized |
| LBP | computed | 28 | L1 | uniform rotation-invariant (riu2), scales (P,R) = (8,1) and (16,2), each histogram L1-normalized |
| HOG | computed | 3780 | L2 | grey 64x128, 8x8 cells, 9 bins, 2x2 blocks, L2-Hys |
| EHD | provided (MPEG-7) | 150 | L1 | 80 local + 5 global + 65 semi-global edge bins, used as provided |
| HTD | provided (MPEG-7) | 43 | L1 | 43-value texture vector (non-standard length), z-score normalized per dimension |
| VGG16 | computed (CNN) | 512 | L2 | torchvision ImageNet VGG16, conv blocks 1-5 on 224x224, global average pooling, L2-normalized |

- Color and LBP are computed after resizing the image so its longest side is
  256 px. HOG resizes to its own 64x128 window.
- The descriptor parameters are written to `artifacts/manifest.json` at indexing
  time and read back by the server, so offline and online vectors are computed
  with exactly the same function and parameters. Uploading `im1.jpg` returns
  image 1 at distance 0.
- **Uploaded images** support color, LBP, HOG and VGG16 (the CNN is loaded at
  server start-up). EHD and HTD are provided
  MPEG-7 data that exist only for database images, so they are greyed out in the
  UI for uploads.
- Histogram intersection is `1 - sum(min(a, b))`. On L1-normalized histograms it
  equals `0.5 * L1`, so it is a true metric and can be indexed by the VP-Tree.

### Combining descriptors

Each distance is divided by that descriptor's scale `s_i`, the median distance
between 2000 random pairs of database images (computed offline). The scaled
distances are then averaged with the user weights:
`D = sum_i w_i * d_i / s_i / sum_i w_i`.
Brute force over `D` is exact. In VP-Tree mode each descriptor's tree returns
`max(10k, 200)` candidates, and their union is re-ranked with the exact `D`.

## Index structure: VP-Tree

`backend/index/vptree.py` is a balanced VP-Tree (median split) with leaf buckets
(512 points, the fastest size measured at N = 25k). The vantage point is chosen among 5 random candidates as the one
with the largest spread of distances. Each child stores the `[min, max]` of
`d(vp, x)` over its points, and a subtree is skipped when the triangle-inequality
lower bound `max(lo - d(q,vp), d(q,vp) - hi)` exceeds the current k-th best
distance. The search is exact, which `tests/test_vptree.py` and the evaluation
check. One tree is built per (descriptor, metric) pair.

## Search features (UI and API)

- Keyword query on Flickr tags (comma-separated, `AND`/`OR`) through an SQLite
  index. With an image query, the keywords filter the candidates, which are then
  ranked by visual distance using brute force on the subset.
- Image query: a database image (id, random gallery), an uploaded image, or any
  result (click it to search again).
- Descriptor checkboxes with a metric and a weight for each, VP-Tree / brute
  force switch, and k.
- **Fuzziness slider** (0-100 %, default 100):
  - *Image search*: the combined distance is min-max normalized to [0, 1] over
    the database, and a result is kept when its normalized distance is
    <= fuzziness x the normalized distance of the K-th result (at most K
    results). The database minimum is the best result's distance, so the rule
    becomes `(d_i - d_1) / (d_K - d_1) <= fuzziness`, with no need for the
    database maximum. 100 % = plain top-K; lower = only matches close to the
    best one, possibly fewer than K. The result count is shown.
  - *Keywords*: typo tolerance with rapidfuzz. Each keyword is expanded to
    the tags whose `fuzz.ratio` similarity is >= `100 - fuzziness x 0.30` (exact
    tags only at 0 %, similarity >= 70 at 100 %, at most 10 tags per keyword).
    The UI shows which tags each keyword matched.
- The response shows the server search time, the round-trip time, the index
  actually used and the number of distance computations. Hovering a result
  shows each descriptor's distance and the image's tags.

API: `GET /api/config`, `GET /api/random`, `GET /api/images/{id}`,
`GET /api/tags/suggest?prefix=`, `POST /api/search` (JSON),
`POST /api/search/upload` (multipart: `file` + `params` JSON). Interactive docs
are at `/docs`.

## Evaluation protocol

- Ground truth: the 24 MIRFLICKR "potential" concept labels.
- **Relevant** = the result shares at least one concept label with the query.
  The query is excluded from its results, and only labelled images are used as
  queries.
- 100 random queries (seed 42). Metrics: P@K, R@K and mAP@K for K = 10, 20, per
  descriptor and metric and for several combinations, plus a random-ranking
  baseline.
- VP-Tree vs brute force: build time, average query time (k = 20), share of
  distance computations, exactness, and scalability with N = 1k to 25k.

Results: `report_assets/evaluation_summary.md` and the `fig_*.png` figures.
